# D4.1 — RecoveryManager Wiring

## Deliverable
D4 — Recovery & Logging

## Prerequisites
- D1 (Orchestrator Core) — `CaptureOrchestrator` class shell with `__init__()`, `start()`, `stop()`
- `OrchestratorConfig` dataclass with recovery-related fields (`capture_restart_delay`, `max_capture_retries`, `encoder_retry_count`)
- `RecoveryManager` implemented and tested in `src/dreamsync/capture/recovery_manager.py`
- `RecoveryConfig` dataclass importable from `recovery_manager.py`
- `CaptureProcessManager` instantiated as `self._capture` in `CaptureOrchestrator.__init__()` (from D2)

## Description

Wire the `RecoveryManager` into `CaptureOrchestrator.__init__()` so that capture process and encoder process failures can be automatically handled during pipeline operation. The `RecoveryManager` wraps the existing `CaptureProcessManager` and provides retry/restart logic with configurable delays and retry limits. The orchestrator derives a `RecoveryConfig` from the unified `OrchestratorConfig`, ensuring all recovery parameters are centrally managed and immutable once the pipeline starts.

This is the foundational wiring step for D4 — subsequent sub-components (D4.2 capture failure recovery, D4.3 encoder failure recovery, D4.6 gap records) all depend on `self._recovery` being available.

## Implementation Details

### File Modified
`src/dreamsync/capture/orchestrator.py`

### Import Addition
```python
from dreamsync.capture.recovery_manager import RecoveryManager, RecoveryConfig
```

### Wiring in `__init__()`

Add the following after `self._capture` is instantiated and before thread creation:

```python
self._recovery = RecoveryManager(
    capture_manager=self._capture,
    config=RecoveryConfig(
        capture_restart_delay=config.capture_restart_delay,
        max_capture_retries=config.max_capture_retries,
        encoder_retry_count=config.encoder_retry_count,
    ),
)
```

### RecoveryConfig Field Mapping

The `RecoveryConfig` dataclass (defined in `recovery_manager.py`) has four fields. Three are explicitly set from `OrchestratorConfig`; the fourth (`gap_strategy`) uses its own default:

| RecoveryConfig field | Type | Default | Source |
|----------------------|------|---------|--------|
| `capture_restart_delay` | `float` | `0.2` | `OrchestratorConfig.capture_restart_delay` |
| `max_capture_retries` | `int` | `5` | `OrchestratorConfig.max_capture_retries` |
| `encoder_retry_count` | `int` | `1` | `OrchestratorConfig.encoder_retry_count` |
| `gap_strategy` | `str` | `"leave"` | Not overridden — uses RecoveryConfig default |

### Alternative: Using `to_recovery_config()`

`OrchestratorConfig` already provides a `to_recovery_config()` convenience method (defined in D1.1). The wiring can alternatively use:

```python
self._recovery = RecoveryManager(
    capture_manager=self._capture,
    config=config.to_recovery_config(),
)
```

Both approaches are equivalent. The explicit construction shown first makes the field mapping visible at the call site; the `to_recovery_config()` approach is more concise. Either is acceptable as long as the resulting `RecoveryConfig` values match the `OrchestratorConfig` values.

### Shared CaptureProcessManager Reference

The `RecoveryManager` receives the **same** `CaptureProcessManager` instance (`self._capture`) that the producer thread reads from. This is critical because when `handle_capture_failure()` calls `self._capture.stop()` then `self._capture.start()`, the producer thread must be able to read from the new `self._capture.stdout` pipe after recovery. The reference sharing ensures the recovery manager operates on the live capture process, not a copy.

### Initialization Order

The full `__init__()` instantiation order relevant to D4.1:

1. `self._config = config` (OrchestratorConfig)
2. `self._capture = CaptureProcessManager(config.to_capture_config())` (D1/D2)
3. `self._recovery = RecoveryManager(capture_manager=self._capture, config=...)` **(D4.1)**
4. `self._logger = PipelineLogger(...)` (D4.4)
5. Buffer, split processor, boundary queue, etc. (D2/D3)
