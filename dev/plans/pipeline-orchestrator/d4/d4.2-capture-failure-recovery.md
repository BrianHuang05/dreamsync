# D4.2 — Capture Failure Recovery

## Deliverable
D4 — Recovery & Logging

## Prerequisites
- D4.1 (RecoveryManager Wiring) — `self._recovery` available in `CaptureOrchestrator`
- D4.4 (PipelineLogger Wiring) — `self._logger` available for recovery event logging
- D2 (Capture Data Path) — `_producer_loop()` implemented, reading from `self._capture.stdout` via `read_chunks()`
- `AudioBuffer` with `signal_eof()` method and `frames_processed` property
- `RecoveryManager.handle_capture_failure()` and `reset_capture_failure_count()` implemented

## Description

Add exception handling to the producer thread's `_producer_loop()` method so that when FFmpeg crashes or the stdout pipe breaks, the pipeline automatically attempts recovery instead of terminating. The recovery flow uses `RecoveryManager.handle_capture_failure()` to stop the dead FFmpeg process, wait a configurable delay, and restart it. On successful recovery, the producer thread recursively re-enters the read loop to resume capturing from the new process's stdout. If retries are exhausted (default 5 consecutive failures), the producer signals EOF on the buffer, allowing the consumer thread to drain remaining data and finalize the last segment gracefully.

This is the most critical recovery path in the pipeline: a single FFmpeg crash during a multi-hour recording session should not lose the entire capture. The recursive re-entry pattern allows recovery to happen transparently without restarting the entire pipeline.

### Producer Loop with Recovery

Replace the existing `_producer_loop()` (from D2) with the recovery-aware version:

```python
def _producer_loop(self) -> None:
    """Read PCM chunks from FFmpeg and push them into the buffer.

    On FFmpeg failure, attempts automatic recovery via RecoveryManager.
    If recovery succeeds, re-enters the loop with the new stdout pipe.
    If retries are exhausted, signals EOF so the consumer drains gracefully.
    """
    try:
        for chunk in read_chunks(self._capture.stdout, self._config.chunk_ms):
            if self._stop_event.is_set():
                break
            self._buffer.put(chunk)
            self._recovery.reset_capture_failure_count()
    except Exception as exc:
        self._logger.recovery_event(
            "capture_failure",
            frame_position=self._buffer.frames_processed,
            error=str(exc),
            error_type=type(exc).__name__,
        )
        recovered = self._recovery.handle_capture_failure(
            frame_position=self._buffer.frames_processed,
        )
        if recovered:
            self._logger.recovery_event(
                "capture_restarted",
                frame_position=self._buffer.frames_processed,
            )
            # Recursive re-entry: read from the new capture.stdout
            self._producer_loop()
            return
        else:
            self._logger.log(
                "ERROR", "recovery", "capture_unrecoverable",
                data={"retries_exhausted": True},
                frame_position=self._buffer.frames_processed,
            )
    finally:
        self._buffer.signal_eof()
```

### Recovery Flow Step-by-Step

1. **FFmpeg crashes** — `read_chunks()` raises an exception (typically `OSError`, `BrokenPipeError`, or `ValueError` from an empty read on a dead pipe).

2. **Log the failure** — `self._logger.recovery_event("capture_failure", ...)` emits a WARNING-level structured log entry with the frame position and error details.

3. **Attempt recovery** — `self._recovery.handle_capture_failure(frame_position=...)`:
   - Increments the consecutive failure counter
   - If counter exceeds `max_capture_retries` (default 5), returns `False`
   - Otherwise: sleeps `capture_restart_delay` seconds (default 0.2), calls `self._capture.stop()`, then `self._capture.start()`
   - Creates a `GapRecord` with the failure frame position and appends it to the internal gap list
   - Returns `True` on success

4. **Resume on success** — If `handle_capture_failure()` returns `True`:
   - Log `"capture_restarted"` event
   - Call `self._producer_loop()` recursively — this enters a new `read_chunks()` loop reading from the fresh `self._capture.stdout`
   - The `return` after the recursive call prevents the `finally` block from signaling EOF prematurely during unwinding

5. **Give up on failure** — If `handle_capture_failure()` returns `False`:
   - Log `"capture_unrecoverable"` at ERROR level
   - Fall through to `finally` block, which calls `self._buffer.signal_eof()`
   - The consumer thread sees the EOF sentinel, drains remaining chunks, finalizes the last encoder, and exits cleanly

### Recursive Re-entry Safety

The recursive depth is bounded by `max_capture_retries` (default 5). Each failed recovery attempt increments the counter inside `RecoveryManager`, so the recursion cannot exceed `max_capture_retries + 1` frames deep. With the default of 5, worst-case stack depth is 6 frames — well within safe limits.

On successful recovery, `reset_capture_failure_count()` is called on each successful chunk read, resetting the counter to 0. This means recovery attempts are only counted when they happen consecutively without any successful reads in between.

### EOF Signal Behavior

The `finally: self._buffer.signal_eof()` ensures EOF is always signaled when the producer exits, regardless of how it exits:
- Normal exit (stop event set) — EOF signals clean shutdown
- Unrecoverable failure — EOF signals drain-and-exit
- Recovered then re-entered — the recursive call's `finally` signals EOF when it eventually exits; the outer `finally` also runs but `signal_eof()` puts another `None` sentinel, which is harmless (the consumer stops on the first one)
