# D4.6 — Gap Records in Metadata

## Deliverable
D4 — Recovery & Logging

## Prerequisites
- D4.1 (RecoveryManager Wiring) — `self._recovery` available, with `gaps` property
- D4.2 (Capture Failure Recovery) — `handle_capture_failure()` creates `GapRecord` entries on recovery
- D2 (Capture Data Path) — `_on_segment_complete()` writes sidecar metadata via `MetadataWriter`
- `GapRecord` dataclass defined in `recovery_manager.py`
- `SegmentMetadata` dataclass with `gaps: list[dict]` field defined in `metadata_writer.py`

## Description

Connect the `RecoveryManager`'s gap tracking to the `SegmentMetadata` sidecar output so that any capture restarts that occurred during a segment are recorded in that segment's JSON sidecar file. When FFmpeg crashes and is restarted (via D4.2), the `RecoveryManager` creates a `GapRecord` with the frame position where the failure occurred. These gap records must be included in the `SegmentMetadata.gaps` field when writing sidecars, so downstream consumers (playback tools, quality analysis scripts) can detect and account for discontinuities in the audio stream.

Gap records are critical for audio integrity verification. A gap indicates that some PCM data was lost between the old and new FFmpeg processes. Even though the gap duration may be unknown (reported as 0 frames by default), the frame position and timestamp allow consumers to identify exactly where in the recording the discontinuity occurred.

### GapRecord Dataclass Reference

The `GapRecord` is defined in `recovery_manager.py`:

```python
@dataclass
class GapRecord:
    start_frame: int
    end_frame: int = 0
    duration_frames: int = 0
    timestamp: float = 0.0
```

Fields:
- `start_frame` — The frame counter value at the moment of failure (from `AudioBuffer.frames_processed`)
- `end_frame` — The frame counter value when capture resumed (set to `start_frame` by default, since the gap length is unknown during a blind restart)
- `duration_frames` — Estimated number of lost frames (default 0, meaning unknown)
- `timestamp` — Wall-clock time of the failure (`time.time()`)

### RecoveryManager.gaps Property

```python
@property
def gaps(self) -> list[GapRecord]:
    return list(self._gaps)
```

Returns a shallow copy of all gap records accumulated since the pipeline started. The list grows monotonically (gaps are never removed during a session).

### Filtering Gaps for a Segment

When writing a segment's sidecar, only include gaps whose `start_frame` falls within the segment's frame range `[start_frame, end_frame)`:

```python
def _gaps_for_segment(self, seg_start: int, seg_end: int) -> list[dict]:
    """Return gap records that fall within the given segment frame range."""
    from dataclasses import asdict
    result = []
    for gap in self._recovery.gaps:
        if seg_start <= gap.start_frame < seg_end:
            result.append(asdict(gap))
    return result
```

def _write_segment_sidecar(

### Sidecar Output Format

When gaps exist, the sidecar JSON includes:

```json
{
  "startFrame": 0,
  "endFrame": 960000,
  "segmentDurationFrames": 960000,
  "segmentDurationSeconds": 20.0,
  "gaps": [
    {
      "start_frame": 480000,
      "end_frame": 480000,
      "duration_frames": 0,
      "timestamp": 1709500000.0
    }
  ],
  "...": "other fields"
}
```

When no gaps exist, the sidecar JSON includes:

```json
{
  "gaps": null,
  "...": "other fields"
}
```

This matches the existing `MetadataWriter._build_payload()` behavior which outputs `"gaps": meta.gaps if meta.gaps else None`.

### Multiple Gaps in One Segment

It is possible for a segment to contain multiple gaps if FFmpeg crashes and recovers multiple times within the same song boundary. The `_gaps_for_segment()` method returns all gaps within the frame range, not just the first one.

### Gaps Spanning Segment Boundaries

A gap's `start_frame` is assigned to exactly one segment. If a capture failure occurs very close to a segment boundary, the gap is assigned to whichever segment contains the `start_frame`. The subsequent segment starts fresh from the new capture process with no gap record (unless another failure occurs within it).

### Edge Cases

1. **No failures during session** — `self._recovery.gaps` returns an empty list. `SegmentMetadata.gaps` is `[]`. Sidecar output shows `"gaps": null`.

2. **Failure before first segment boundary** — Gap falls within segment 0's range `[0, first_boundary)`. Only segment 0's sidecar contains the gap.

3. **Failure during last segment** — Gap falls within the final segment's range. The last sidecar contains the gap record.

4. **Recovery fails (retries exhausted)** — No `GapRecord` is created for the final failed attempt (only successful recoveries create records). The pipeline drains and stops, so the last segment's sidecar may be incomplete.
