## Prerequisites
- D5.1 complete: `capture_orchestrator` variable exists in `session.py`, constructed from `CaptureOrchestrator`
- `CaptureOrchestrator.start()` — spawns producer/consumer threads and FFmpeg subprocess
- `CaptureOrchestrator.shutdown()` — orderly teardown: stops threads, flushes encoder, writes final sidecar
- `CaptureOrchestrator.stats` — property returning `dict` with `segments_completed`, `elapsed_seconds`, `drift_corrections`
- `CaptureOrchestrator.start_periodic_timing(fetch_fn)` — starts a background timer that periodically calls `fetch_fn()` and feeds timing data into the boundary queue
- `SpotifyQueueWatcher` with `get_queue()` method returning `QueueSnapshot | None`
- `QueueSnapshot` has `.currently_playing` (SpotifyTrack | None) and `.queue` (tuple of SpotifyTrack)
- `SpotifyTrack` has `.name`, `.artist`, `.album`, `.duration_ms`
- `PlaybackState` has `.progress_ms`

## Description

This sub-component wires the `CaptureOrchestrator` lifecycle into the `run_session()` function in two places:

1. **Before the live loop** — Start the orchestrator and (if Spotify is available) start periodic timing updates that feed the boundary queue with song duration and playback position data from Spotify.

2. **In the `finally` block** — Shut down the orchestrator and print a summary of capture statistics (segments saved, elapsed time, drift corrections).

The old code had a simple `capture_pipeline.flush()` in the finally block. The new orchestrator has a more comprehensive `shutdown()` method that handles all cleanup internally (stops FFmpeg, drains the buffer, flushes the encoder, writes final metadata). After shutdown, the `stats` property provides a summary dict.

The periodic timing integration is the bridge between Spotify's playback data and the capture pipeline's boundary detection. A `_fetch_timing()` closure reads the latest queue from `SpotifyQueueWatcher` and formats it into the `timing_data` dict expected by `CaptureOrchestrator.start_periodic_timing()`.

## Implementation Details

### Start Block — Insert Before Live Loop (Before Section 6)

Insert after the capture orchestrator construction (D5.1) and after signal handling setup (section 5), but before the live loop (section 6):

```python
# 5b. Start capture orchestrator
if capture_orchestrator:
    capture_orchestrator.start()

    # Wire periodic timing updates from Spotify queue
    if spotify_watcher:
        def _fetch_timing():
            """Build timing_data dict from Spotify queue for boundary detection."""
            queue = spotify_watcher.get_queue()
            if queue is None:
                return None

            current = queue.currently_playing
            if current is None:
                return None

            # Build song durations list: current track + upcoming queue
            song_durations = [current.duration_ms / 1000.0]
            for track in queue.queue:
                song_durations.append(track.duration_ms / 1000.0)

            # Get current playback position from the latest playback state
            playback = spotify_watcher.playback_state
            current_playback_time = 0.0
            if playback is not None and playback.progress_ms is not None:
                current_playback_time = playback.progress_ms / 1000.0

            return {
                "song_durations": song_durations,
                "current_playback_time": current_playback_time,
                "current_song": {
                    "song_title": current.name,
                    "artist": current.artist,
                    "album": current.album,
                },
            }

        capture_orchestrator.start_periodic_timing(_fetch_timing)
        print("Capture: periodic timing sync with Spotify enabled")
```

Note: The capture orchestrator is shut down **first** (before `spotify_watcher.stop()`) to ensure timing data is still available during the final flush. The orchestrator's `shutdown()` method internally stops the periodic timing thread, so no timing callbacks will fire after shutdown returns.

### `_fetch_timing()` Return Format

The `timing_data` dict returned by `_fetch_timing()` must match the format expected by `TimingIntegrator`:

```python
{
    "song_durations": [float, ...],       # Duration in seconds for current + upcoming tracks
    "current_playback_time": float,       # Current position in seconds within current track
    "current_song": {
        "song_title": str,                # Track name
        "artist": str,                    # Artist name
        "album": str,                     # Album name
    },
}
```

If `_fetch_timing()` returns `None`, the periodic timing thread skips that update cycle. This happens when:
- Spotify queue is not available yet (initial startup delay)
- No track is currently playing (paused/stopped state)

### Stats Dict Format

The `capture_orchestrator.stats` property returns:

```python
{
    "segments_completed": int,    # Number of songs saved to disk
    "elapsed_seconds": float,     # Total capture duration in seconds
    "drift_corrections": int,     # Number of boundary drift corrections applied
}
```

### Ordering Constraints

1. `capture_orchestrator.start()` must be called **after** `spotify_watcher.start()` (section 4d) so that the watcher is ready to provide queue data.
2. `capture_orchestrator.start()` must be called **before** the live loop (section 6) so that capture is running before audio processing begins.
3. `capture_orchestrator.shutdown()` must be called **before** `spotify_watcher.stop()` in the finally block, so the orchestrator can make final timing queries during its flush.
