# D3.2 — TimingIntegrator Wiring

## Deliverable
D3 — Boundary Control Path

## Prerequisites
- D1.1 — `OrchestratorConfig` dataclass with `safety_margin_frames`, `sample_rate`, and `timing_refresh_interval` fields
- D1 — `CaptureOrchestrator.__init__()` shell accepting `OrchestratorConfig`
- D2 — `AudioBuffer` wired as `self._buffer` in the orchestrator with `frames_processed` property
- `BoundaryQueue` implemented in `src/dreamsync/capture/boundary_queue.py`
- `TimingIntegrator` implemented in `src/dreamsync/capture/timing_integrator.py`

## Description

This sub-component wires the `BoundaryQueue` and `TimingIntegrator` into the `CaptureOrchestrator.__init__()` method. These two objects form the entry point of the boundary control path: the `BoundaryQueue` holds the ordered list of upcoming segment split points, and the `TimingIntegrator` converts external timing data (song durations, playback position) into frame-level boundaries that it pushes into the queue.

The wiring must ensure:
1. A single `BoundaryQueue` instance is shared between the `TimingIntegrator`, the `DynamicSplitProcessor` (D3.1), and the `DriftDetector` (D3.4).
2. The `TimingIntegrator` receives a `get_current_frame` lambda that reads from the `AudioBuffer`'s `frames_processed` property, giving it real-time awareness of where the pipeline is in the audio stream.
3. Configuration values (`safety_margin_frames`, `sample_rate`, `timing_refresh_interval`) are sourced from `OrchestratorConfig`, not hardcoded.

## Implementation Details

### File
`src/dreamsync/capture/orchestrator.py`

### Imports
```python
from dreamsync.capture.boundary_queue import BoundaryQueue
from dreamsync.capture.timing_integrator import TimingIntegrator
```

### Wiring in `__init__()`

Add the following to `CaptureOrchestrator.__init__()`, after the `AudioBuffer` has been created (since the lambda references `self._buffer`):

```python
# --- Boundary control path ---
self._boundary_queue = BoundaryQueue(
    safety_margin_frames=config.safety_margin_frames,
)

self._timing = TimingIntegrator(
    boundary_queue=self._boundary_queue,
    get_current_frame=lambda: self._buffer.frames_processed,
    sample_rate=config.sample_rate,
    refresh_interval=config.timing_refresh_interval,
)
```

### Object Relationships

```
OrchestratorConfig
    |
    +-- safety_margin_frames --> BoundaryQueue(safety_margin_frames=...)
    |                                |
    +-- sample_rate      ---------->|
    +-- timing_refresh_interval --> TimingIntegrator(
    |                                   boundary_queue=self._boundary_queue,

    |                                   sample_rate=config.sample_rate,

    |                               )

AudioBuffer (self._buffer)
    |

```

### `get_current_frame` Lambda

The lambda `lambda: self._buffer.frames_processed` is evaluated lazily each time `TimingIntegrator` needs the current frame position (during `update()` and periodic refresh ticks). This is important because:

- At `__init__()` time, `frames_processed` is 0 and the buffer may not have started receiving data yet.
- The lambda captures `self._buffer` by reference, so it always reflects the live frame count.
- `AudioBuffer.frames_processed` is thread-safe (protected by an internal lock), so calling it from the `TimingIntegrator`'s timer thread is safe.

### Ordering Constraints

The `BoundaryQueue` and `TimingIntegrator` must be created **after** `self._buffer` (the `AudioBuffer`) because the lambda references `self._buffer`. The typical `__init__()` order is:

1. Store `config`
2. Create `PipelineLogger`
3. Create `AudioBuffer` (`self._buffer`)
4. Create `BoundaryQueue` (`self._boundary_queue`)
5. Create `TimingIntegrator` (`self._timing`)
6. Create `DriftDetector` (`self._drift`) — D3.4
7. Create `DynamicSplitProcessor` (`self._split`) — uses `self._boundary_queue`

### Cleanup in `stop()`

The `TimingIntegrator` runs a background `threading.Timer` for periodic refresh. The orchestrator's `stop()` method must call:

```python
self._timing.stop()
```

This cancels the timer and prevents callbacks after the pipeline has shut down. This should be added to whatever teardown/stop method is defined in D1.
