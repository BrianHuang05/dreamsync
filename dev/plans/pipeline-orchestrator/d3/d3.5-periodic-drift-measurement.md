# D3.5 — Periodic Drift Measurement

## Deliverable
D3 — Boundary Control Path

## Prerequisites
- D3.4 — `DriftDetector` wired as `self._drift` in `CaptureOrchestrator`
- D2 — Consumer loop (`_consumer_loop`) implemented, reading chunks from `AudioBuffer` and passing them to `DynamicSplitProcessor`
- D2 — `AudioBuffer` wired as `self._buffer` with `frames_processed` property
- D3.1 — `DynamicSplitProcessor` wired as `self._split`
- `PipelineLogger` wired as `self._logger` with `timing_event()` method
- `DriftMeasurement` dataclass with `drift_frames`, `drift_seconds`, `level` fields
- `time.monotonic()` available for wall-clock measurement

## Description

The `DriftDetector` only produces measurements when explicitly called. This sub-component integrates drift measurement into the orchestrator's consumer loop so that drift is checked periodically during live capture.

Checking drift on every chunk (every ~100 ms) would be wasteful since meaningful drift accumulates slowly. Instead, the consumer loop tracks a chunk counter and calls `_check_drift()` every `DRIFT_CHECK_INTERVAL_CHUNKS` chunks (default 100, which equals approximately 10 seconds at 100 ms chunks). This interval balances responsiveness (catching drift before it grows too large) against overhead (each measurement involves floating-point arithmetic and a potential queue scan for correction).

The `_check_drift()` method:
1. Computes elapsed wall-clock time since capture started using `time.monotonic()`.
2. Calls `DriftDetector.measure_and_correct()` with the actual frame count and elapsed time.
3. Logs the measurement via `PipelineLogger.timing_event()` for diagnostics.

If drift exceeds the correction threshold, `measure_and_correct()` automatically adjusts future boundary positions in the `BoundaryQueue`. The consumer loop does not need to take any additional action; the `DynamicSplitProcessor` will naturally pick up the adjusted boundaries on its next `peek_next()` call.

### Timing Diagram

```
Consumer Loop Iteration
    |
    +-- chunk = self._buffer.get()
    +-- self._split.process_chunk(chunk)
    +-- chunks_since_drift_check += 1
    |
    +-- if chunks_since_drift_check >= 100:
            |
            +-- self._check_drift()
            |       |
            |       +-- elapsed = time.monotonic() - self._start_time
            |       +-- m = self._drift.measure_and_correct(
            |       |       actual_frames, elapsed, current_frame
            |       |   )
            |       +-- self._logger.timing_event("drift_check", ...)
            |
            +-- chunks_since_drift_check = 0
```

## Implementation Details

### File
`src/dreamsync/capture/orchestrator.py`

### Import
```python
import time
```

### Module-Level Constant

```python
DRIFT_CHECK_INTERVAL_CHUNKS = 100  # ~10 seconds at 100 ms chunks
```

This is a module-level constant rather than a config field because it is an internal implementation detail that does not need user-facing configuration. At 100 ms per chunk (the default `chunk_ms`), 100 chunks equals 10 seconds. If `chunk_ms` is changed, the wall-clock interval changes proportionally, but the number of chunks between checks remains fixed.

### Modified `_consumer_loop()`

The consumer loop (introduced in D2) is modified to add the drift-check counter:

```python
def _consumer_loop(self) -> None:
    """Consume PCM chunks from the buffer, split at boundaries.

    Runs in the consumer thread.  Exits when the buffer yields
    ``None`` (EOF signal from the producer).
    """
    chunks_since_drift_check = 0

    while True:
        chunk = self._buffer.get()
        if chunk is None:
            break

        self._split.process_chunk(chunk)

        chunks_since_drift_check += 1
        if chunks_since_drift_check >= DRIFT_CHECK_INTERVAL_CHUNKS:
            self._check_drift()
            chunks_since_drift_check = 0

    self._split.finish()
```

**Key points:**
- The counter is a local variable, not an instance attribute, since it is only relevant within the consumer loop's lifetime.
- The drift check runs **after** `process_chunk()`, not before, so the frame counter reflects the most recent chunk.
- On EOF (`chunk is None`), the loop exits without a final drift check. A final drift measurement could be added but is not required since the pipeline is shutting down.

### `_check_drift()` Method

```python
def _check_drift(self) -> None:
    """Measure current drift and auto-correct if threshold exceeded."""
    elapsed = time.monotonic() - self._start_time
    m = self._drift.measure_and_correct(
        actual_frames=self._buffer.frames_processed,
        elapsed_wall_seconds=elapsed,
        current_frame=self._buffer.frames_processed,
    )
    self._logger.timing_event(
        "drift_check",
        frame_position=self._buffer.frames_processed,
        drift_seconds=m.drift_seconds,
        drift_frames=m.drift_frames,
        level=m.level,
    )
```

**Parameter explanation:**
- `actual_frames`: Total frames captured since pipeline start, from `AudioBuffer.frames_processed`.
- `elapsed_wall_seconds`: Wall-clock time since `self._start_time` (set when `start()` is called), measured via `time.monotonic()` for monotonic clock guarantees (immune to system clock adjustments).
- `current_frame`: Same as `actual_frames`. Passed separately because `measure_and_correct()` uses it for the `correct()` call to determine which boundaries are within the safety margin.

### `self._start_time` Initialization

The `_start_time` attribute must be set when the pipeline starts capturing. This should be done in the orchestrator's `start()` method (or equivalent lifecycle method from D1):

```python
def start(self) -> None:
    # ... other startup logic ...
    self._start_time = time.monotonic()
    # ... start threads ...
```

If `_start_time` is not yet defined in the orchestrator (it may be introduced in D2 or D1), it must be added as part of this sub-component.

### Logging Output

Each drift check produces a structured log entry via `PipelineLogger.timing_event()`:

```json
{
    "timestamp": "2024-01-15T10:30:00.000Z",
    "level": "INFO",
    "category": "timing",
    "event": "drift_check",
    "data": {
        "drift_seconds": 0.042,
        "drift_frames": 2016,
        "level": "acceptable"
    },
    "frame_position": 4800000
}
```

The `level` field in the data payload reflects the drift severity: `"acceptable"`, `"warning"`, `"correction"`, or `"critical"`. This is the `DriftMeasurement.level` string, not the log level.

### What Happens at Each Drift Level

| `DriftMeasurement.level` | Drift magnitude | Action taken |
|--------------------------|----------------|--------------|
| `"acceptable"` | < 0.1s | Logged at DEBUG. No correction. |
| `"warning"` | 0.1s - 0.5s | Logged at WARNING. No correction. |
| `"correction"` | 0.5s - 2.0s | Logged at WARNING. `DriftDetector.correct()` shifts all unlocked future boundaries by `drift_frames`. |
| `"critical"` | > 2.0s | Logged at ERROR. Correction applied but magnitude suggests systemic issue (device clock skew, buffer underrun, etc.). |
