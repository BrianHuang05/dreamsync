- D2 — `AudioBuffer` wired as `self._buffer` with `frames_processed` property

- `BoundaryQueue.replace_future(entries, current_frame)` respects locked entries

## Description

Boundary locking is a safety mechanism that prevents the `TimingIntegrator` or `DriftDetector` from modifying boundaries that are about to be consumed by the `DynamicSplitProcessor`. Without locking, a boundary at frame 100,000 could be moved or removed by a timing update at frame 99,500 (just 500 frames / 10 ms before the split processor reaches it), causing an inconsistent split or a missed boundary.

The `BoundaryQueue` already implements the locking logic: `update_locks(current_frame)` marks any boundary within `safety_margin_frames` of `current_frame` as `locked=True`, and `replace_future()` preserves locked entries when replacing the queue contents. What this sub-component does is **call** `update_locks()` at the right time in the consumer loop so that locks are kept current as the pipeline advances through the audio stream.

### Safety Margin

The default `safety_margin_frames` is 24,000 frames, which equals 0.5 seconds at 48 kHz. This means any boundary within 0.5 seconds of the current playback position is locked and cannot be modified. The margin provides a buffer for:

- **Thread scheduling latency**: The `TimingIntegrator` timer thread may be delayed by OS scheduling.
- **Chunk processing time**: The consumer loop may take a few milliseconds to process each chunk.
- **Queue operation atomicity**: Although individual queue operations are locked, a read-modify-write sequence (snapshot entries, adjust, replace) is not atomic.

### Lock Update Frequency

`update_locks()` is called on **every chunk** in the consumer loop, not on the drift-check interval. This is important because:

1. At 100 ms chunks and a 0.5 s safety margin, there are only 5 chunks between a boundary entering the safety margin and being consumed. If locks were only updated every 100 chunks (10 seconds), a boundary could pass through the entire safety margin unlocked.
2. `update_locks()` is cheap: it iterates entries until it finds one past the threshold, then stops (entries are sorted). For a typical queue of 2-10 entries, this is negligible overhead.

### Interaction with Other Components

```
Consumer Loop (each chunk):
    |
    +-- self._split.process_chunk(chunk)         # may peek/pop boundaries
    +-- self._boundary_queue.update_locks(...)    # lock approaching boundaries
    |
    |   (concurrently, from timer thread)
    +-- TimingIntegrator._tick()
    |       |
    |       +-- self._queue.replace_future(...)   # locked entries preserved
    |
    |   (periodically, from consumer loop)
    +-- DriftDetector.measure_and_correct(...)
            |
            +-- self._queue.replace_future(...)   # locked entries preserved
```

The lock update runs **after** `process_chunk()` in each iteration. This ordering ensures that:
- Boundaries consumed by `process_chunk()` (via `pop_next()`) are already removed before the lock scan.
- Boundaries approaching the current frame are locked before the next potential `replace_future()` call from the timer thread.

### Modified `_consumer_loop()`

Add a single line to the consumer loop, after `process_chunk()` and before the drift-check logic:

```python
def _consumer_loop(self) -> None:
    """Consume PCM chunks from the buffer, split at boundaries.

    Runs in the consumer thread.  Exits when the buffer yields
    ``None`` (EOF signal from the producer).
    """
    chunks_since_drift_check = 0

    while True:
        chunk = self._buffer.get()
        if chunk is None:
            break

        self._split.process_chunk(chunk)
        self._boundary_queue.update_locks(self._buffer.frames_processed)

        chunks_since_drift_check += 1
        if chunks_since_drift_check >= DRIFT_CHECK_INTERVAL_CHUNKS:
            self._check_drift()
            chunks_since_drift_check = 0

    self._split.finish()
```

### The Added Line

```python
self._boundary_queue.update_locks(self._buffer.frames_processed)
```

This single call:
1. Reads the current frame position from `AudioBuffer.frames_processed`.
2. Computes the threshold: `current_frame + safety_margin_frames`.
3. Iterates sorted entries, marking those with `frame_position <= threshold` as `locked = True`.
4. Stops at the first entry past the threshold (entries are sorted by `frame_position`).

### BoundaryQueue.update_locks() Reference

From `boundary_queue.py` (already implemented):

```python
def update_locks(self, current_frame: int) -> None:
    """Mark boundaries within safety margin as locked."""
    with self._lock:
        threshold = current_frame + self._safety_margin
        for entry in self._entries:
            if entry.frame_position <= threshold:
                entry.locked = True
            else:
                break
```

Key properties:
- **Thread-safe**: Protected by `self._lock`, same lock used by `peek_next()`, `pop_next()`, and `replace_future()`.
- **Idempotent**: Calling `update_locks()` multiple times with the same `current_frame` has no additional effect (already-locked entries remain locked).
- **Efficient**: O(k) where k is the number of entries within the safety margin (typically 0-1).

### How Locks Protect Boundaries

**Scenario without locking:**
```
Frame 95,000: Boundary at 100,000 exists in queue (unlocked)
Frame 95,500: TimingIntegrator.update() calls replace_future() with new boundaries
              -> Boundary at 100,000 is REMOVED, replaced with boundary at 120,000
Frame 100,000: DynamicSplitProcessor expects boundary at 100,000 -> MISSED
```

**Scenario with locking:**
```
Frame 76,000: update_locks(76_000) -> threshold = 76_000 + 24_000 = 100_000
              -> Boundary at 100,000 is LOCKED
Frame 95,500: TimingIntegrator.update() calls replace_future() with new boundaries
              -> Boundary at 100,000 is PRESERVED (locked), new boundaries added after it
Frame 100,000: DynamicSplitProcessor finds boundary at 100,000 -> SPLIT CORRECT
```

### Edge Cases

1. **Empty queue**: `update_locks()` on an empty queue is a no-op (the `for` loop body never executes). No special handling needed.

2. **All boundaries locked**: If all entries are within the safety margin, they are all marked locked. A subsequent `replace_future()` preserves all of them and appends any new boundaries after. This is correct behavior — it means all upcoming boundaries are imminent.

3. **Boundary at exact current frame**: A boundary with `frame_position == current_frame` is within the safety margin (since `current_frame <= current_frame + safety_margin`) and is locked. However, `DynamicSplitProcessor.process_chunk()` handles this case by consuming it immediately (`frames_to_boundary <= 0` branch).
