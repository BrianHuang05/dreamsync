## Description

These tests verify the pipeline's drift detection and correction mechanism. Drift occurs when the actual rate of audio capture diverges from the expected rate -- for example, if the audio device's clock runs slightly fast or slow relative to the system clock, or if FFmpeg drops frames during high CPU load.

The `DriftDetector` compares `actual_frames` (from the `AudioBuffer` frame counter) against `expected_frames` (computed from `elapsed_wall_seconds * sample_rate`). If the drift exceeds the correction threshold (default 0.5 seconds = 24000 frames at 48kHz), the detector adjusts all unlocked future boundaries in the `BoundaryQueue` to compensate.

Two scenarios are tested:
1. **No correction when drift is small**: If the drift is below the correction threshold, no boundaries are modified and `corrections_applied` remains 0.
2. **Correction applied when drift exceeds threshold**: Simulated slow capture (fewer frames than wall time would predict) triggers boundary adjustment.

Since we control both the frame counter and the wall time in tests, we can precisely simulate any drift magnitude without actual timing issues.

### Drift Simulation Strategy

We do **not** need real timing or real audio capture to test drift. Instead, we call `DriftDetector.measure()` directly with controlled parameters:

```python
# Simulate: 10 seconds of wall time, but only 9.4 seconds of frames captured
# This is a drift of -0.6s (below expected = "slow capture")
actual_frames = int(9.4 * 48000)    # = 451200 frames
wall_seconds = 10.0                  # 10 seconds elapsed
# Expected frames = 10.0 * 48000 = 480000
# Drift = 451200 - 480000 = -28800 frames = -0.6s
```

For the no-correction test:
```python
# Simulate: drift of only 0.05s (below warning threshold)
actual_frames = int(9.95 * 48000)   # = 477600 frames
wall_seconds = 10.0
# Drift = 477600 - 480000 = -2400 frames = -0.05s
```

### Boundary Adjustment Verification

When `DriftDetector.correct()` is called with a "correction"-level drift, it:
1. Reads all entries from the `BoundaryQueue`
2. For each unlocked entry, subtracts `drift_frames` from `frame_position`
3. Calls `replace_future()` with the adjusted entries

We can verify this by checking boundary positions before and after correction:

```python
# Before correction: boundary at frame 480000 (10s)
# Drift is -28800 frames (-0.6s) -- capture is slow
# After correction: boundary should move to 480000 - (-28800) = 508800
# Wait, correction subtracts drift_frames, and drift_frames is negative:
# new_position = 480000 - (-28800) = 508800
# This moves the boundary later to account for slow capture.
```

Actually, reviewing the `DriftDetector.correct()` code more carefully:

```python
offset = measurement.drift_frames  # e.g., -28800 for slow capture
entry.frame_position -= offset      # 480000 - (-28800) = 508800
```

So for slow capture (negative drift), boundaries are pushed later. For fast capture (positive drift), boundaries are pulled earlier. This is correct: if capture is slow, the songs arrive later than expected, so boundaries should be later.

## Test Cases

- [ ] `test_no_correction_under_threshold` — Create a `BoundaryQueue` with 3 boundaries at frames `[240000, 480000, 720000]` (5s, 10s, 15s). Create a `DriftDetector` with default thresholds (`warning_threshold=0.1`, `correction_threshold=0.5`, `critical_threshold=2.0`) and pass the boundary queue. Simulate capture that is 0.05 seconds slow: call `measure(actual_frames=int(9.95*48000), elapsed_wall_seconds=10.0)`. Assert: the returned `DriftMeasurement` has `level == "acceptable"` (0.05 < 0.1 warning threshold). Assert: `corrections_applied == 0`. Call `measure_and_correct(actual_frames=int(9.95*48000), elapsed_wall_seconds=10.0, current_frame=int(9.95*48000))`. Assert: `corrections_applied` is still 0 (no correction triggered). Assert: boundary positions are unchanged -- `queue.entries()` still shows `[240000, 480000, 720000]`. This proves that small drift does not trigger unnecessary boundary adjustments.

- [ ] `test_correction_applied_over_threshold` — Create a `BoundaryQueue` with 2 boundaries at frames `[480000, 960000]` (10s, 20s at 48kHz). Create a `DriftDetector` with the boundary queue. Simulate capture that is 0.6 seconds slow over 10 seconds: call `measure_and_correct(actual_frames=int(9.4*48000), elapsed_wall_seconds=10.0, current_frame=int(9.4*48000))`. Assert: the returned `DriftMeasurement` has `level == "correction"` (0.6 > 0.5 correction threshold). Assert: `corrections_applied >= 1`. Read the boundary queue entries. Assert: boundary positions have been adjusted -- they should no longer be at the original `[480000, 960000]` positions. Specifically, since `drift_frames = int(9.4*48000) - int(10.0*48000) = 451200 - 480000 = -28800`, the correction subtracts this offset, so new positions should be `480000 - (-28800) = 508800` and `960000 - (-28800) = 988800` (boundaries pushed later to account for slow capture). Assert: the queue entries' `frame_position` values match the expected adjusted positions (within a small tolerance for integer arithmetic).
