## Description

These tests verify the pipeline's ability to handle real-time changes to segment boundaries while audio capture is in progress. This is the key differentiator between a static split tool and DreamSync's live capture pipeline: as new Spotify timing data arrives, the pipeline dynamically adjusts where it will split the audio stream.

Three scenarios are tested:
1. **Mid-capture boundary update**: Boundaries are changed after capture has started but before the split point is reached. The pipeline should split at the updated position, not the original.
2. **Track change with immediate split**: An unexpected track change creates a boundary at the current frame position, causing an immediate segment rotation.
3. **Safety margin enforcement**: Boundaries that are within the safety margin of the current frame position are locked and cannot be modified by `replace_future()`.

These tests require careful timing control. Since the pipeline processes PCM in chunks, we need to feed a specific amount of data, pause, update boundaries, then feed the remainder. This is achieved by manually stepping through the pipeline rather than using the full `run()` convenience method.

### Manual Pipeline Stepping Helper

For dynamic boundary tests, we cannot use `SplitProcessor.run()` because we need to pause mid-stream to update boundaries. Instead, we step through the pipeline manually:

```python
def _step_pipeline(
    processor: SplitProcessor,
    pcm_data: bytes,
    chunk_ms: int = 100,
    pause_after_frames: int | None = None,
    pause_callback: callable = None,
) -> None:
    """Feed PCM through the processor with an optional mid-stream pause.

    Parameters
    ----------
    pause_after_frames:
        If set, pause after this many frames have been processed
        and invoke pause_callback before continuing.
    pause_callback:
        Called during the pause (e.g. to update boundaries).
    """
    from io import BytesIO
    stream = BytesIO(pcm_data)
    processor.start()
    paused = False

    for chunk in read_chunks(stream, chunk_ms):
        processor.process_chunk(chunk)

        if (
            not paused
            and pause_after_frames is not None
            and processor.current_frame >= pause_after_frames
            and pause_callback is not None
        ):
            pause_callback()
            paused = True

    processor.finish()
```

### Dynamic SplitProcessor with BoundaryQueue

The standard `SplitProcessor` takes a static `boundaries: list[int]`. For dynamic boundary tests, we need a version that reads from `BoundaryQueue` at runtime. There are two approaches:

**Approach A**: Use `SplitProcessor` with a mutable list that we modify externally (the `_boundaries` attribute is a list that can be mutated).

**Approach B**: Build a `DynamicSplitProcessor` wrapper (if implemented in D3) that reads from `BoundaryQueue.peek_next()`.

The tests should use whichever approach is implemented in D3. The key assertion is that changing boundary positions before they are reached causes the split to happen at the new position.

```python
# Approach A: Mutate the internal boundaries list
processor = SplitProcessor(
    boundaries=[240000, 480000],  # Initial: splits at 5s and 10s
    start_encoder=start_encoder,
)

# After 3s of data, update boundaries to [192000, 384000] (4s and 8s)
def update_boundaries():
    processor._boundaries[0] = 192000  # Move first split from 5s to 4s
    processor._boundaries[1] = 384000  # Move second split from 10s to 8s
```

## Test Cases

- [ ] `test_boundary_update_mid_capture` — Generate multi-song PCM with `durations = [10.0, 10.0]` (20 seconds total, enough room for boundary changes). Set initial boundaries at `[240000]` (split at 5 seconds). Start feeding PCM through the processor. After 3 seconds of data have been processed (144000 frames), update the boundary to `[192000]` (split at 4 seconds). Continue feeding remaining PCM. Assert: the first segment file contains exactly `192000 * 4 = 768000` bytes (4 seconds), NOT `240000 * 4 = 960000` bytes (5 seconds). Assert: the second segment contains the remaining bytes. Assert: total bytes across both files equals `len(pcm_data)`. This proves the pipeline respects dynamically updated boundaries.

- [ ] `test_track_change_triggers_immediate_split` — Generate sine PCM with `duration_seconds=10.0` (one continuous song). Set up the pipeline with no initial boundaries (empty list). Start feeding PCM. After 3 seconds of data (144000 frames), simulate a track change by inserting a boundary at the current frame position: add frame position 144000 to the boundaries list (or call `on_track_change()` on a `TimingIntegrator` that pushes a boundary at the current frame). Continue feeding remaining PCM. Assert: 2 output files are produced. Assert: file 0 contains approximately `144000 * 4 = 576000` bytes (3 seconds). Assert: file 1 contains the remaining data (~7 seconds). This verifies that `on_track_change()` creates an immediate split at the current playback position.

- [ ] `test_locked_boundary_not_modified` — Create a `BoundaryQueue` with `safety_margin_frames=24000` (0.5s). Add a boundary at frame 48000 (1.0s). Advance the simulated current frame to 30000 (0.625s -- within 0.5s safety margin of the boundary at 48000). Call `replace_future(new_boundaries=[BoundaryEntry(frame_position=96000, segment_index=0)], current_frame=30000)`. Assert: the original boundary at 48000 survives (it is locked because `48000 <= 30000 + 24000 = 54000`). Assert: the new boundary at 96000 is also present. Assert: the queue now contains both boundaries: [48000, 96000]. Then generate PCM and run through SplitProcessor with boundaries derived from the queue. Assert: the first split happens at frame 48000 (the locked boundary), not at 96000. This proves that safety-margin-locked boundaries are preserved when `replace_future()` is called.
