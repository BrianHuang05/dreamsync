# Deliverable 5.2: Drift Detection & Resync

## Phase

[Phase 5: Metadata, Logging & Recovery](../phase5-metadata-recovery.md)

## Prerequisites

- Phase 4 complete (dynamic rolling window operational)
- Deliverable 5.4 complete (logging system available)

## Description

Detect and correct timing drift between the planned segment boundaries and actual audio capture timing. Drift occurs when the external timing data and the capture frame counter diverge due to clock differences, API latency, or playback irregularities.

### Sources of Drift

1. **Clock skew:** System clock vs audio device clock run at slightly different rates
2. **API latency:** External timing data arrives with delay
3. **Playback irregularities:** Buffering, seeking, or pausing in the source application
4. **Accumulated rounding:** Frame rounding errors compound over many segments

### Drift Measurement

On each timing refresh, compare expected vs actual frame position:

```python
expected_frame = elapsed_wall_time * sample_rate
actual_frame = frame_counter.frames_processed
drift_frames = actual_frame - expected_frame
drift_seconds = drift_frames / sample_rate
```

### Drift Thresholds

| Threshold       | Value       | Action                              |
|-----------------|-------------|-------------------------------------|
| Acceptable      | < 0.1s      | Log at DEBUG level, no action       |
| Warning         | 0.1s - 0.5s | Log at WARNING level                |
| Correction      | 0.5s - 2.0s | Adjust future boundaries            |
| Critical        | > 2.0s      | Log at ERROR level, force resync    |

### Correction Strategy

When drift exceeds the correction threshold:

1. Compute the drift offset in frames
2. Adjust all future (unlocked) boundaries by the drift offset
3. Log the correction with before/after boundary values
4. Reset the drift accumulator

### Optional: Silence Detection

For advanced drift correction, detect silence between tracks to confirm actual track transitions:

- Monitor PCM amplitude over a sliding window
- If amplitude drops below threshold for >0.5s, flag as potential track boundary
- Compare detected silence with planned boundaries

This is optional and can be deferred.

## Completion Criteria

1. Drift is measured on every timing refresh and logged
2. Drift below 0.1s triggers no action
3. Drift between 0.5s and 2.0s triggers automatic boundary adjustment
4. Drift above 2.0s triggers force resync with error-level log
5. Boundary adjustments respect safety margins (locked boundaries unchanged)
6. Drift correction is logged with before/after boundary values
